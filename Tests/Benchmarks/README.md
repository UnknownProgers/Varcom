# Varcom performance benchmarks

This console project uses BenchmarkDotNet 0.15.8 and targets .NET 8. It is not a unit-test
project and is not packaged with Varcom. Registrations for handlers and the operation owner
are generated by the same source generator shipped with the library.

Run from the repository root in Release:

```sh
# Verify all setups and expected handler work without running timing measurements.
dotnet run --project Tests/Benchmarks/Benchmarks.csproj -c Release -- --verify

# Initial survey; use the default job below before drawing conclusions about small differences.
dotnet run --project Tests/Benchmarks/Benchmarks.csproj -c Release -- --job short --filter '*'

# Adaptive default job for a focused follow-up.
dotnet run --project Tests/Benchmarks/Benchmarks.csproj -c Release -- --filter '*PipelineBenchmarks*'
```

Add `--artifacts /absolute/path` to choose an output directory. Otherwise BenchmarkDotNet
uses BenchmarkDotNet.Artifacts, ignored by Git. Run only one measurement process at a time;
do not run tests or builds concurrently with timing measurements.

## What is measured

- PipelineBenchmarks: one complete enqueue/drain batch. BatchSize is 1, 32, 128 or 256.
  Compare typed 4/56/128-byte payloads, individual text submissions and one prebuilt text
  sequence containing the same commands. **Mean is time per batch, not per command.**
  Divide by BatchSize to report average cost per command, including its share of Update.
- OperationBenchmarks: one operation per invocation. All text cases include Enqueue and
  Update; immediate variable reads do not use the queue. Queued variable reads consume
  the result through a cached callback, while the other methods observe owner state.
  The eight explicit/default argument cases perform the same handler arithmetic.
- RegistryBenchmarks: one text submission and Update with 1, 128 or 1024 registered
  methods. The target name and executed work stay the same for every registry size.

The typed handlers all add one integer to a long counter. On the measured x64 runtime,
SmallCommand is 4 bytes, LargeCommand is 56 bytes, and Payload128Command is 128 bytes.
Both larger payloads include one CmdString view; setup verifies the 128-byte size. Command
creation, text creation, registrations and capacity growth happen in setup. The default
capacity is 128; the 256-command case warms the grown buffers before measurement.

Inputs are constant/prebuilt strings. Measurements exclude input construction, cold start,
registration, capacity growth and application work beyond the fixture handlers. They do
not measure isolated Enqueue versus isolated Update, engine frame cost, network latency
or thread safety. Results are machine/runtime-specific; ShortRun has limited statistical
precision. Inspect Mean, Error and StdDev, not just ratios. MemoryDiagnoser complements
the exact GC-allocation regression checks in Core.Tests.

A command is constructed during Update; its scalar values are validated when enqueued
and parsed again during execution. The explicit/default argument comparison measures the
combined input-handling cost, not the second parse in isolation.

BenchmarkDotNet references:
[Running benchmarks](https://benchmarkdotnet.org/articles/guides/how-to-run.html),
[Jobs and accuracy](https://benchmarkdotnet.org/articles/configs/jobs.html).

## Diagnostic Enqueue / Update split

```sh
dotnet run --project Tests/Benchmarks/Benchmarks.csproj -c Release -- --phases
```

This separate diagnostic runner measures the two phases on 128-command batches, with
2,000 warmup batches and five samples of 10,000 batches. It reports the median ns/command
for each phase and allocated bytes in the timed loops. Both inputs invoke the same eight
integer handler with the same values (defaults versus explicit input). Handler work is
verified after measurement. Input construction and registration are outside measurement.

These are Stopwatch diagnostics, not isolated BenchmarkDotNet microbenchmarks. Timestamp
and enqueue-loop overhead are included and amortized across the batch. They identify
where a change acts; use matching BenchmarkDotNet end-to-end runs to validate improvements.
Phase medians need not sum to a BenchmarkDotNet mean. Do not run this simultaneously with
other timing measurements.
